## 1. Контекст задачи (исходный кейс хакатона)

**Партнёр:** ТОО «Электрокомплект» (ekt.kz)
**Кейс:** Автоматический расчёт заказов поставщикам для пополнения склада

### 1.1 Проблема
Менеджер отдела закупа сейчас рассчитывает потребность в пополнении склада вручную в Excel. Из-за трудоёмкости расчёт проводится нечасто, что приводит к:
- избыточным запасам по одним позициям;
- дефициту по другим;
- искажению расчёта разовыми крупными заказами (в т.ч. продажа большого объёма одному клиенту), что ведёт к лишним издержкам на хранение и упущенным продажам.

### 1.2 Пользователь и ключевой сценарий
Основной пользователь — **менеджер отдела закупа**.
Сценарий: запускает расчёт по складу/категории → получает список рекомендованных заказов с обоснованием по каждой позиции → проверяет и корректирует при необходимости → утверждает заказ.

### 1.3 Задача (как сформулирована в кейсе)
Разработать сервис, который на основе:
- истории продаж,
- сезонности,
- устойчивого роста спроса,
- текущих остатков,
- товаров в пути,
- категорий товаров,
- прогноза по приросту,
- оценки упущенного спроса в периоды отсутствия товара (stockout),

формирует рекомендованные заказы поставщикам, а также **выявляет и исключает разовые крупные заказы** (включая крупные продажи одному клиенту) из расчёта регулярной потребности.

### 1.4 Вход / выход (по кейсу)
**Вход:** история продаж (дата, артикул, количество, обезличенный клиент, цена), текущие остатки по складам, периоды stockout по артикулам, справочник поставщиков и сроков поставки, материальная ведомость из 1С.

**Выход:** список рекомендованных заказов (артикул, поставщик, рекомендуемое количество, обоснование, срочность) — таблица/дашборд с экспортом.

### 1.5 Must have (критерии проверки жюри)
1. Расчёт базовой потребности по каждому артикулу с учётом всех источников данных — изменение любого источника (например, товаров в пути) должно отражаться на результате.
2. Учёт сезонности и устойчивого роста спроса — для сезонного товара прогноз должен отражать сезонный паттерн, а не просто среднее.
3. Оценка и компенсация упущенного спроса в периоды stockout — расчётная потребность должна корректироваться в большую сторону по сравнению с "сырыми" продажами.
4. Выявление и исключение разовых крупных заказов — искусственно добавленный в тест разовый крупный заказ **не должен** существенно поднимать рекомендуемое регулярное количество. **(Жюри почти наверняка тестирует именно этот пункт руками.)**
5. Итоговый список, сгруппированный по поставщикам, с кратким обоснованием по каждой позиции.

### 1.6 Ограничения
- **Нельзя** автоматически отправлять заказ поставщику без подтверждения менеджера.
- **Нельзя** использовать в расчётах неанонимизированные данные о клиентах.
- Обязательно: приватность данных, объяснимость расчёта, устойчивость к аномалиям/выбросам, совместимость выходного формата с текущей учётной системой (1С).

## 2. Принятые решения по продукту (что решили в обсуждении)

### 2.1 Формат — веб-приложение
Решено делать **веб-приложение** (фронтенд + бэкенд), а не браузерное расширение и не десктоп-приложение.
Причина: у пользователя нет существующего сайта/интерфейса, к которому логично "прицепиться" расширением — сценарий самостоятельный (запуск расчёта → таблица → корректировка → утверждение), поэтому нужен полноценный отдельный дашборд.

### 2.2 Загрузка данных — два режима
1. **«Формат 1С»** — жёсткий шаблон под выгрузку из учётной системы партнёра (материальная ведомость + продажи + остатки). Точный формат уточняется с партнёром по ходу хакатона.
2. **«Свой файл (быстрый анализ)»** — универсальный Excel/CSV по собственному шаблону команды, не зависящий от партнёра. Это основной сценарий для демо и тестирования, так как не зависит от того, успеет ли партнёр прислать реальную выгрузку.

Оба режима парсятся разными парсерами, но дальше используют один и тот же расчётный пайплайн.

### 2.3 Дополнительные фичи (добавлены сверх базового кейса)
- **Подбор поставщика/товара на рынке для оптовой закупки** — сравнение текущего поставщика с альтернативами на рынке (цена/условия), по каждой позиции в заказе.
- **Аналитика трендов** — графики спроса по категориям, сезонность, топ растущих/падающих категорий, тепловая карта риска дефицита по складам/категориям.
- **ИИ-анализ спроса и сезонности** — текстовое аналитическое резюме на естественном языке по каждому артикулу (не просто число, а объяснение: тренд, сезонность, влияние stockout, рекомендация).

Все три пункта технически объединены в единый **ИИ-слой (LLM-оркестратор)** — общий модуль, через который проходят: генерация обоснований, аналитическое резюме, поиск рыночных предложений (через LLM + web search). Это упрощает архитектуру и хорошо продаётся на демо как «единый ИИ-движок платформы».

### 2.4 Реализация подбора поставщика на рынке (техническое решение)
Так как нет доступа к реальным API маркетплейсов/B2B-площадок за ограниченное время хакатона, выбран подход: **OpenAI API (Responses API) с инструментом web search** + **Structured Outputs (JSON mode)**. Промпт вида "найди оптовые предложения на [товар] в Казахстане, верни структурированный JSON с ценой/поставщиком/условиями" — ответ уже приходит в заданной JSON-схеме и не требует парсинга свободного текста.
**Важно:** точность такого поиска не гарантирована на 100%, на демо и в презентации это стоит называть "рекомендательным ориентиром", а не источником истины.

### 2.5 Технический стек и инструменты (актуально)

Команда использует ключи и инструменты, выданные на хакатоне: **OpenAI API credits**, **ChatGPT Pro**, **Codex**, а также промо-доступ к **NVIDIA Brev** и **NVIDIA Build** (активированы про запас, в основной план не входят).

**Бэкенд — `feature/data-core` (Человек 1)**
- Python 3.11 + **FastAPI**
- **pandas** — парсинг Excel/CSV, весь расчётный пайплайн
- **statsmodels** — прогноз с учётом сезонности/тренда (экспоненциальное сглаживание или сезонная декомпозиция; выбрано вместо Prophet ради скорости внедрения)
- **SQLite** или in-memory хранение на время сессии — без лишней инфраструктуры
- **openpyxl** — чтение Excel-шаблонов (оба режима загрузки)

**Фронтенд — `feature/ui-analytics` (Человек 2)**
- **Vanilla HTML + CSS + JS** — без build-шага (Vite/webpack); снижает риск проблем с окружением в сжатые сроки и проще для быстрой итерации через Codex
- Один SPA-файл (или несколько HTML-файлов) с переключением вкладок показом/скрытием блоков — роутер не нужен
- **Chart.js** через CDN — графики истории продаж, сезонности, трендов по категориям; тепловая карта риска — кастомная отрисовка на grid/canvas поверх тех же данных
- **TailwindCSS (CDN play-версия)** — быстрая вёрстка без написания CSS с нуля
- `fetch()` — обращение к API бэкенда по контракту данных (раздел 4)
- React рассматривался, но отклонён в пользу vanilla-стека: сложность интерфейса (таблицы, графики, формы) не оправдывает накладные расходы на тулинг и state-менеджмент при двух участниках и ограниченном времени хакатона

**ИИ-слой (модуль `ai_service`, внутри ветки Человека 2)**
- **OpenAI API**, модель **gpt-4o** или **gpt-4.1**
- Генерация обоснований по артикулу, аналитическое резюме по сезонности/трендам — обычный chat completion с промптом на основе полей `reasoning` из контракта данных
- Подбор поставщика на рынке — **Responses API + web search tool + Structured Outputs**, схема ответа: `[{supplier, price, moq, lead_time, source_url}]`
- Хранить ключ OpenAI в переменных окружения (`.env`), не коммитить в репозиторий

**Codex**
- Используется **обоими участниками** как ассистент в терминале/IDE для написания парсеров, React-компонентов, эндпоинтов, дебага — часть рабочего процесса, а не архитектурный компонент продукта
- Вход в тот же аккаунт ChatGPT Pro, что был выдан на хакатоне

**NVIDIA Brev / NVIDIA Build**
- **Не входят в основной стек.** Активировать промокоды стоит на всякий случай, но использовать только как fallback: если кредиты OpenAI API закончатся раньше дедлайна, через NVIDIA Build можно быстро поднять бесплатный NIM-эндпоинт с открытой LLM вместо OpenAI. GPU (Brev) проекту не требуется — расчётный пайплайн (statsmodels/pandas) полностью работает на CPU

Это единая точка синхронизации между расчётным ядром и визуалом/аналитикой. Человек 2 (UI/аналитика) верстает интерфейс на основе этой структуры, используя моковые данные, **не дожидаясь** готовности расчётного ядра.

    {
      "sku": "ABC-123",

      "warehouse": "Склад №1",
      "recommended_qty": 120,
      "urgency": "critical",
      "reasoning": {
        "base_demand": 80,
        "seasonality_factor": 1.4,
        "stockout_compensation": 15,
        "trend_growth": 0.05,
        "explanation_text": "текст обоснования, сгенерированный ИИ-слоем"
      },
      "history": [
        {"date": "2026-01-01", "qty": 12},
        {"date": "2026-02-01", "qty": 15}

## 5. Разделение работы на две ветки

### Ветка `feature/data-core` — Человек 1
### Ветка `feature/ui-analytics` — Человек 2

## 6. ТЗ — Человек 1: Данные и расчётное ядро (`feature/data-core`)

### Цель
Реализовать загрузку данных, их валидацию и полный расчётный пайплайн, отдающий результат в формате контракта данных (раздел 4) через API.

### Состав работ

**6.1. Загрузка и парсинг данных**
- Эндпоинт загрузки файла (`/upload`), приём Excel/CSV.
- Два режима парсинга:
  - «Формат 1С» — парсер под шаблон выгрузки партнёра (материальная ведомость, продажи, остатки, поставщики/сроки поставки).
  - «Свой файл» — парсер под собственный упрощённый шаблон (для демо/тестирования, не зависит от партнёра).
- Подготовить и приложить скачиваемый образец шаблона для режима «Свой файл».
- Валидация структуры: проверка обязательных колонок (артикул, дата, количество, цена, обезличенный клиент, склад, остаток), понятные ошибки при несоответствии.
- Превью после загрузки: количество строк, диапазон дат, найденные проблемы (пропуски, дубликаты).

**6.2. Расчётный пайплайн**
- Расчёт базовой потребности по артикулу с учётом: истории продаж, текущих остатков, товаров в пути, категории товара, прогноза по приросту.
- Учёт сезонности и устойчивого тренда роста спроса (модель прогноза — на выбор: экспоненциальное сглаживание, Prophet, либо простая сезонная декомпозиция — приоритет скорости реализации над сложностью модели).
- Оценка и компенсация упущенного спроса в периоды stockout (по данным о периодах отсутствия товара на складе).
- Детектор аномалий / разовых крупных заказов, в т.ч. крупных продаж одному клиенту (статистический подход: z-score/IQR на уровне артикул+клиент+дата), с исключением их из расчёта регулярной потребности.
- Устойчивость алгоритма к выбросам и аномалиям во входных данных в целом (не только к разовым заказам).

**6.3. API-слой**
- `POST /upload` — загрузка файла, возврат превью/результата валидации.
- `POST /calculate` — запуск расчёта по складу/категории.
- `GET /orders` — получение списка рекомендаций в формате контракта данных (раздел 4).
- `GET /anomalies` — список выявленных и исключённых разовых заказов.
- `POST /orders/{sku}/adjust` — приём ручной корректировки количества от менеджера (с полем "причина").
- `POST /orders/approve` — фиксация утверждённого заказа (без автоматической отправки поставщику — только подготовка к экспорту).

**6.4. Хранение**
- Для хакатона: держать датасет в памяти на время сессии либо SQLite — не усложнять постоянной БД без необходимости.
- Обеспечить, что данные о клиентах остаются обезличенными на всех этапах расчёта.

### Критерии приёмки (self-check перед сдачей)
- Изменение любого из входных источников (например, объёма товаров в пути) видимо влияет на итоговый расчёт.
- Для товара с выраженной сезонностью прогноз отражает сезонный паттерн, а не среднее.
- Для артикула с stockout расчётная потребность выше, чем по "сырым" продажам.
- Искусственно вставленный в тест разовый крупный заказ не приводит к существенному росту рекомендуемого количества — **обязательно протестировать этот сценарий вручную перед демо**.
- Каждая позиция в `/orders` сопровождается структурированным обоснованием (`reasoning`), достаточным для генерации текста ИИ-слоем на стороне Человека 2.

## 7. ТЗ — Человек 2: Визуал, графики, ИИ-анализ, аналитика (`feature/ui-analytics`)

### Цель
Реализовать пользовательский интерфейс поверх контракта данных (раздел 4), включая графики, ИИ-генерируемые обоснования, аналитику трендов и подбор поставщика на рынке.

### Состав работ

**7.1. Дашборд заказов**
- Таблица рекомендованных заказов: артикул, поставщик, рекомендуемое количество, срочность (цветовой индикатор), краткое обоснование.
- Фильтры: склад, категория, поставщик, срочность.
- Кнопка запуска расчёта (вызывает `/calculate` на бэкенде Человека 1).
- Блок "Найти лучшую цену на рынке" по каждой позиции (см. п. 7.4).

**7.2. Детализация по артикулу**
- Раскрывающаяся карточка/страница по клику на позицию.
- График истории продаж с наложением сезонного паттерна.
- Отметка периодов stockout на графике.
- Блок обоснования числа (человекочитаемый вывод из поля `reasoning`).
- Блок "ИИ-анализ" — расширенное текстовое резюме от LLM: тренд, сезонность, влияние дефицита, итоговая рекомендация (см. п. 7.5).

**7.3. Аномалии / Исключённые заказы**
- Отдельная вкладка со списком исключённых разовых заказов (`excluded_anomalies` из контракта).
- Возможность вручную вернуть позицию в расчёт, если менеджер не согласен с исключением.
- Это самый вероятный пункт ручной проверки жюри — сделать максимально наглядным.

**7.4. Подбор поставщика на рынке**
- Модуль ИИ-слоя: запрос к Claude API с web search тулом по названию/категории товара.
- Промпт должен возвращать структурированный JSON: поставщик, цена, условия (минимальная партия, срок), источник.
- UI: сравнение текущего поставщика с 1-3 найденными альтернативами.
- Возможность менеджеру выбрать альтернативу вместо дефолтного поставщика при утверждении заказа.
- На демо и в презентации явно обозначать как "рекомендательный ориентир", не как гарантированно точные данные.

**7.5. ИИ-слой (общий модуль `ai_service`)**
- Единая точка входа для всех LLM-запросов проекта: генерация обоснований, аналитическое резюме по артикулу, поиск рыночных предложений.
- Не размазывать промпты по разным местам кода — держать в одном модуле с чёткими функциями (например: `generate_reasoning()`, `generate_seasonality_summary()`, `find_market_alternatives()`).

**7.6. Аналитика / Тренды**
- Графики спроса по категориям во времени (помесячно/по неделям).
- Топ растущих / падающих категорий.
- Тепловая карта "склад × категория" по уровню риска дефицита.

**7.7. Корректировка и утверждение**
- Экран ручной правки количества с полем "причина корректировки".
- Группировка по поставщикам для утверждения заказа целиком.
- Кнопка "Утвердить" — вызывает `/orders/approve`, **не отправляет** заказ поставщику автоматически (по ограничению кейса).

**7.8. Экспорт / История заказов**
- Экспорт утверждённого заказа в Excel/CSV.
- Простой лог истории прошлых расчётов/утверждений (можно минимально, если не хватает времени).

### Критерии приёмки (self-check перед сдачей)
- Интерфейс полностью работает на моковом JSON независимо от готовности бэкенда (до момента интеграции).
- Каждая строка в таблице заказов сопровождается понятным обоснованием, доступным для просмотра в развёрнутом виде.
- ИИ-обоснования и аналитические резюме не звучат как шаблонная заглушка — реально используют цифры из `reasoning`.
- Вкладка аномалий наглядно показывает, что и почему исключено — этот экран нужно явно показать на демо.

## 8. Демо-сценарий (для финальной презентации)

1. Загрузка тестовых данных (режим "Свой файл").
2. Превью данных → запуск расчёта.
3. Дашборд: таблица рекомендаций, открыть детализацию по одному артикулу с сезонностью и ИИ-анализом.
4. Вкладка аномалий: показать, что искусственно вставленный разовый крупный заказ был корректно исключён из регулярного расчёта.
5. Подбор поставщика на рынке для одной позиции — показать альтернативу.
6. Аналитика трендов — общий вид по категориям.
7. Ручная корректировка количества → утверждение → экспорт.
